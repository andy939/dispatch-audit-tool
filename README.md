# 派工案件抽查規劃工具

每月從機關派工系統下載案件、分析、勾選要抽查的項目、並在地圖上依捷運站分群規劃路線用的本機網頁工具。純前端、不需伺服器，複製整個資料夾到別台電腦就能繼續用。

## 目前狀態摘要（新對話開始前先看這裡）

**版面結構**：主頁面（`index.html`）是左側 5 個頁籤導覽 + 右側內容區（不是舊版那種整頁往下捲）：
- 📥 資料匯入（本月案件匯入按鈕 + 上月抽查資料匯入按鈕 + 地理編碼設定 + 案件總覽——**所有匯入動作都集中在這個頁籤**，不管是本月還是上月的資料，見下面「上月抽查匯入搬到資料匯入頁籤」那條紀錄）
- 🔍 本月案件管理（左：案件項目分析勾選篩選 + 案件清單表格；右固定 300px：📍 附近案件）——頁籤名稱跟「上月抽查管理」對稱，之前叫「案件清單」，見下面改名那條紀錄
- 📋 上月抽查管理（左：合併後的抽查清單表格；右固定 300px：📍 附近案件）——純顯示/操作頁面（跟本月案件管理對本月案件的角色一樣），獨立於本月資料的第二套資料集，細節見下面「新增上月抽查管理頁籤」那條紀錄
- 🚇 依捷運站分群（左：分群清單；右固定 300px：📍 附近案件）
- 🚩 路線規劃（❤️ 已標記案件清單（最後確認/取消標記用）+ 規劃結果 + 選地圖截圖 + 匯出 CSV/Word 按鈕，整區佔滿寬度，沒有右側附近案件側欄）

「📍 附近案件」不是獨立頁籤，是內嵌在「案件清單」「上月抽查管理」「依捷運站分群」這三個頁籤裡的同一塊內容（`.nearby-embed-panel`／`.nearby-embed-hint`，`renderNearbyPanel()` 一次更新所有現存容器，且會同時搜尋 `state.cases` 跟 `getLastMonthCases()` 兩個資料集）。「路線規劃」頁籤原本也有一份，後來拿掉了（見下面「路線規劃新增已標記案件清單」那條紀錄）。地圖獨立在 `map.html`，兩邊用 `localStorage` + `storage` 事件即時同步。

**目前的當前版本號**：`index.html`/`map.html` 裡所有本地 `?v=N` 快取破壞參數目前是 **v=69**——**改 `app.js`／`map.js`／`style.css` 任何一個之後，一定要把這兩個檔案裡全部的 `?v=N` 一起 bump 成 `N+1`**（`sed -i 's/v=N/v=N+1/g' index.html map.html`），不然使用者瀏覽器可能還在用快取的舊版。

**資料模型關鍵點**（避免重新踩雷）：
- `state.filter.category/district/agency` 存的是**排除集合**（Set 裡的值＝不顯示），不是「要顯示的值」——預設空集合＝全部勾選＝全部顯示，取消勾選才把值加進 Set。這份排除設定案件清單表格跟依捷運站分群清單共用（`applyCategoryFilters()`），排除某項目後兩邊清單要同時濾掉、不能一邊看得到一邊看不到；但只影響「顯示」，`state.cases` 本身不變，地圖跟路線規劃刻意不套用，仍是全部已匯入案件永遠同步（避免跟 ♡ 標記路線的機制搞混）
- ♡ 標記（`state.marked`）只用來挑選「之後要排路線」的案件，跟案件清單/地圖/分群清單顯示範圍完全無關（沒有勾選機制了，全部匯入案件永遠都會顯示/同步到地圖）
- **上月抽查管理是完全獨立的第二套資料集**（`state.lastMonthFullList`／`state.lastMonthAuditList`，合併結果用 `getLastMonthCases()` 現算，不額外存一份），跟本月的 `state.cases` 不共用、不合併，只有 ♡/🚫（`state.marked`/`state.rejected`）、`state.geocache`、附近案件搜尋、地圖同步是共用機制——合併後案件的 `id` 一律加「抽」字前綴（例如 `抽2026073110149`，原始編號存在 `realId`），避免跟本月案件的 id 撞在一起污染標記狀態
- 🚫 標記（`state.rejected`，`toggleRejected()`）：「暫時否決、不列入抽查考量」，純粹是顯示層的樣式標記（那一列背景變白、文字變淺灰），不碰 `state.cases`、不影響篩選/路線規劃/CSV 匯出等任何其他機制——跟 ♡ 標記、案件項目排除設定都是各自獨立、互不干擾的三件事。**例外**：地圖點位的淡化顯示是刻意同步的（見下面「🚫 同步到地圖點位」那條紀錄），透過 `LS_REJECTED`／`storage` 事件跟主視窗共用，`map.js` 只用它來調淡點位的透明度，不影響其他任何地圖邏輯（座標、路線、統計都不受影響）
- `lastRoute = { startStation, order }` 是規劃好路線後的記憶體資料，`exportRoute()`／`exportRouteWord()` 都靠這個
- `COLORS` 色盤在 `app.js`／`map.js` 各存一份，**兩份必須完全一樣**（否則同一個案件項目在主視窗徽章跟地圖點位顏色會不一致）；目前是 Google Material Design 色盤的 12 色 500 色階（使用者要求參考 Google 地圖的配色風格，但 Google 地圖本身圖標配色沒有公開色碼表，改採 Google 自家的 Material Design 標準色系），刻意不含灰/黑
- `FIXED_COLORS`（`app.js`／`map.js` 各存一份，同樣兩邊必須完全一樣）：「鄰里無主垃圾清運」「道路散落物或油漬處理」這兩項固定用灰階（淺灰／深灰），不走 `COLORS` 雜湊自動配色，因為使用者是抽查流程裡最後才查驗的兩項，想跟其他項目的高飽和色視覺上區分開來；`colorFor()` 會先查這個表，查不到才落回雜湊配色
- 案件項目名稱畫面上一律用 `truncateCategory()` 截到最多 10 個中文字＋「…」，完整名稱放 `title`

**踩過的坑，別再犯**：
1. **絕對不要把 `display:flex` 直接放在 `<td>` 或 `<tr>` 上**——瀏覽器會把它拉出表格版面計算，不再跟同一列共用列高，造成分隔線對不齊。flex 排版一律包一層內部 `<div>`。
2. **多列且要對齊的資料一定要用真正的 `<table>`＋`<colgroup>`，不要用「每一列各自 `display:grid`」**——後者每一列是獨立的格線容器，欄寬各自依那一列內容決定，列與列之間不保證對齊（`.case-row`／依捷運站分群踩過這個坑，最後改回真表格才解決）。CSS Grid 的 `%` 欄寬加上一個額外的固定 px 欄位（例如 ♡ 那欄）容易總和超過 100% 造成溢出，要用 `fr` 或直接改用表格。
3. **地圖底圖圖磚（OSM／Google）沒辦法用 `html2canvas` 等技術截圖**——OSM 的圖磚伺服器沒開放 CORS，Google 地圖的使用條款禁止擷取地圖影像存成檔案，兩邊都會讀到一片空白/灰色。地圖截圖功能改成讓使用者自己截圖（Win+Shift+S）後用 Ctrl+V 貼上，不要再嘗試自動擷取。
4. **這個瀏覽器測試環境（Claude Browser 工具）的畫面沒有真的顯示出來（compositing 沒在跑）**，`computer{action:"screenshot"}` 會逾時失敗，`elementFromPoint`／滑鼠座標點擊在這個環境下不可靠（常出現座標對不上的假結果）。驗證改用 `getBoundingClientRect()`、`getComputedStyle()`、直接 `dispatchEvent`／檢查 DOM 狀態，不要依賴視覺截圖或真實座標點擊來驗證。
5. 匯入的 xlsx 案件編號欄位可能被 Excel 換行過（尾端多一個看不見的 `\n`），已經在 `loadState()` 裡用 `migrateCases()` 自動清理舊資料，`parseWorkbookFile()` 解析新資料時也會 `.trim()`，但如果之後又遇到「案件對不到、點了沒反應」，記得檢查 `dataset.id` 跟 `c.id` 是不是真的完全相等的字串。

**外部 CDN 依賴**（全部透過 `<script src="https://...">` 載入，沒有 npm/build step）：SheetJS(xlsx.full.min.js, cdnjs)、Leaflet(unpkg)、`leaflet.gridlayer.googlemutant`（選用 Google 底圖時動態載入）、`docx`(jsdelivr，路線規劃匯出 Word 用)。

**目前待處理／可能需要接續的事**：使用者原本想提供一份參考格式 Word 檔（`J:\8研考會\41 派工抽查\202604 派工\11504中正.docx`／`11504萬華.docx`）讓匯出格式完全比照，但那個檔案讀取時 Windows 回報「The file or directory is corrupted and unreadable」（J 槽網路磁碟疑似有問題，不是這個工具能修的），目前 Word 匯出格式是照使用者口述欄位設計的——如果對方那邊檔案能正常開啟、且跟目前格式有差異，可能會再回來要求調整排版。

## 檔案說明

| 檔案 | 用途 |
|---|---|
| `index.html` | 主頁面：匯入 xlsx、統計分析、案件清單、依捷運站分群建議、路線規劃、匯出 CSV |
| `map.html` | 地圖頁面，從主頁按鈕另開視窗，會自動同步主頁匯入的全部案件與地理編碼結果 |
| `app.js` | 主頁面邏輯 |
| `map.js` | 地圖頁面邏輯（含地理編碼） |
| `style.css` | 共用樣式 |
| `data.js` | 自動產生，內含捷運站座標（給 map.html 用） |
| `mrt_stations.json` | 捷運站座標原始資料 |
| `build_data.py` | 選用小工具：重新產生 `data.js` 的捷運站資料、印出 xlsx 統計（需要 Python，非必要，主要流程都在網頁上完成） |

## 使用方式

1. 直接用瀏覽器（建議 Chrome 或 Edge）開啟 `index.html`（雙擊即可，不需架伺服器）。頁面預設是空的，不會自動帶入舊資料。
2. 點右上角「匯入本月 xlsx 案件檔」，選擇從派工系統下載的 xlsx（**原始未篩選的匯出檔可以直接匯入**，程式會自動掃描找出含「案件編號」的欄位標題列，不管它在第幾列）
3. 上方會顯示案件總覽、依項目/行政區/承辦機關的分析（點列可篩選下方清單，再點一次取消；點開才會展開明細，預設是收合的）
4. **匯入後全部案件都會自動同步到地圖，不需要勾選任何東西**（案件清單固定每頁 10/20/50 筆可選，用上一頁/下一頁翻頁）。清單每一列最後面有 ♡，是專門用來標記「之後要排路線」的案件，跟要不要顯示在地圖上完全無關——沒標記也一樣會在地圖上
5. 點右上角「🗺️ 開啟地圖視窗」另開地圖視窗，按「定位案件座標」進行地理編碼（會定位全部已匯入案件，不限有無標記 ♡）
6. 主頁面下方「依鄰近捷運站分群建議」會自動列出全部已定位案件的分群結果（不需要切換視窗，地圖那邊定位完會自動同步過來），距離捷運站 500 公尺內的案件會用綠色特別標示，每筆案件最後面一樣有 ♡ 可以標記
7. **雙向跳轉**：點案件清單或分群建議中的任一案件，地圖視窗會飛到對應位置；點地圖上的標記，也會跳回主頁面清單並反白該筆案件，同時主頁面「📍 點選地圖案件的周邊清單」會列出以該案件為中心、周邊 500 公尺內的其他案件
8. **規劃查訪路線**：在案件清單或分群清單按 ♡ 標記要排路線的案件，標好後到「建議查訪路線」區塊，可選擇「起點捷運站」（例如從你要搭捷運抵達的那一站開始），按「規劃路線」會自動算出一個盡量不繞路的拜訪順序（案件不多時是全部排列組合找最短、案件多時用最近鄰+2-opt），並把路線畫在地圖上——會先顯示直線示意，背景查詢實際步行路線後自動換成貼合道路的路徑（查不到時維持直線示意）；重新整理頁面後之前規劃好的路線（含起點）也會自動還原顯示；也可以按「匯出路線 CSV」把排好的順序、地址、站間距離存成檔案
9. 需要的話可以「匯出目前清單 CSV」，會依目前的篩選/搜尋條件匯出案件（不受分頁影響），可匯入 Google 我的地圖
10. **地址可以直接編輯**：如果案件的「發生地址」寫得不夠精確導致定位不到（例如系統原始地址跟案件內容講的地點不一致、或缺路段/巷弄），把滑鼠移到那一格會出現 ✏️，點下去改成你認為對的地址，Enter 或按「✓ 儲存」存檔（Esc 或「✕ 取消」放棄修改）。存檔後會自動觸發跟其他操作一樣的同步機制，已經開著的地圖視窗會自動用新地址重新判斷是否需要定位，不用手動重新整理
11. 不想要目前資料了，按「清除現有資料」可以整個清空重來

## 換電腦使用注意事項

- **資料存在瀏覽器的 localStorage，不是存在檔案裡**，所以複製資料夾到新電腦後，之前匯入的案件、♡ 標記、地理編碼結果都不會跟著過去，需要在新電腦上重新「匯入本月 xlsx 案件檔」。
- 需要能上網（地圖圖磚、地理編碼、以及頁面用到的 SheetJS/Leaflet 函式庫都是從網路 CDN 載入），沒有網路的話統計分析、匯出 CSV 仍可正常使用，但地圖跟定位功能會無法使用。
- 若瀏覽器封鎖彈出視窗，「開啟地圖視窗」按鈕可能沒反應，記得允許這個網站的彈出視窗。

## 已知限制

- 預設用免費的 OpenStreetMap/Nominatim 地理編碼，每筆案件查詢間隔約 1.1 秒（尊重使用限制），案件較多時定位需要一些時間。主頁「⚙️ 地理編碼設定」可貼 Google Maps 平台的 API 金鑰改用 Google Geocoding API（需自己申請、綁信用卡開帳單），速度快很多且沒有這個延遲；地圖底圖也可以一起換成 Google 地圖。
- OSM 涵蓋率不如 Google 地圖，部分地址可能查無資料，或只能約略定位到路段（地圖上會用虛線標示、清楚註明「約略位置」）。
- 步行路線圖用的是 `routing.openstreetmap.de` 這個免費公共 OSRM 服務，跟 Nominatim 一樣是社群提供、沒有保證的服務水準，尖峰時段查詢較慢或偶爾失敗都是正常的，失敗時會自動維持直線示意，不影響其他功能。
- **只有真正定位失敗、或只查到約略位置且後來換了地理編碼服務的地址才會重新查詢**，其餘已精確定位的不會每次都重查；真正查無資料的（例如「XX路-YY路」路口交叉點這種不是正式門牌格式的地址）建議手動到 Google 地圖確認。

- ✅ 巷弄本身在 OSM 沒資料時，會再退一步只查「主要道路名稱」定位（例如「裕民一路40巷11號」查不到就退回查「裕民一路」）
- ✅ 路口交叉點格式地址（「A路-B路」，含「N段」路名如「東華街二段-公舘路」）：偵測到這種格式會拆成兩條路分別查詢座標，並在地圖彈窗/分群清單清楚標示「路口交叉點估算位置」
  - 修正：一開始每條路只抓 Nominatim 回傳的第一筆代表點就取中點，但一條路在 OSM 常被切成好幾段不相連的 way，抓到不對的路段會導致算出的路口位置差了一兩公里。改成每條路都抓多筆(limit=6)、把完整線型攤成座標點，兩條路各自的所有點兩兩比對，找真正離彼此最近的一對點才取中點
